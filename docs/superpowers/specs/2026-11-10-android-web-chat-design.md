# Android-First Web Chat Design

**Status:** Approved by the user on 2026-11-10; implementation is governed by the companion plan.

## Intent

Give the user a usable, phone-first browser chat for directing Autonomous Dev AI from an Android phone. The first vertical slice should connect the real Eve agent runtime to the official Eve Web Chat interface, stream responses, and preserve conversations as durable Eve sessions.

## Goals

- Scaffold the official Eve Web Chat integration using `eve add channel/web`.
- Use its generated Next.js app and Eve's supported web client rather than inventing a parallel chat protocol.
- Make the chat comfortable on narrow Android screens: responsive layout, readable messages, large touch targets, and a composer that remains usable with the on-screen keyboard.
- Connect the chat to a real, narrowly scoped planning agent.
- Support starting a conversation, streaming a reply, and reopening an existing session through its session URL.
- Keep model credentials and secrets out of source control.
- Keep the app private; do not expose an unauthenticated production agent endpoint.
- Preserve the existing Eve/TypeScript project foundation and CI checks.

## Non-goals for this milestone

- No autonomous repository edits, shell execution, deployments, purchases, or other external actions.
- No GitHub write access or code-generation tools yet.
- No multi-agent orchestration, custom long-term memory provider, billing UI, or file uploads.
- No native Android app; the deliverable is a responsive web app usable in Chrome on Android.
- No production deployment until authentication and model credentials are configured and verified.

## Proposed architecture

- **Runtime:** existing Eve framework and TypeScript project.
- **Web app:** Next.js generated by the official Eve Web Chat channel scaffold.
- **Chat transport:** Eve's built-in HTTP/web channel and supported frontend client. Use the generated integration and avoid custom protocol code unless the scaffold requires a narrow adaptation.
- **Agent behavior:** planning-only instructions. The agent turns a request into a clear goal, assumptions, ordered steps, risks/dependencies, and verifiable acceptance criteria. It must distinguish unknowns from facts and must not claim to have edited or tested code.
- **Session history:** Eve durable sessions and session IDs; the UI should resume a conversation from its URL rather than inventing a separate database for the first milestone.
- **Authentication:** use the official Web Chat setup's Sign in with Vercel path if the linked project and account permissions support it. This creates a private team-scoped sign-in. If that prerequisite is unavailable, keep production deployment blocked until an equally protective authentication method is selected; never ship an open chat endpoint.
- **Model access:** use Eve's supported model configuration and environment-based credentials. Do not commit API keys or silently incur paid usage. The runtime must show a clear setup error when model access is missing. Actual model usage may be billable depending on the selected provider and account.

## Approaches considered

1. **Official Eve Web Chat scaffold (selected):** `eve add channel/web` generates the Next.js chat app and channel integration. Lowest custom code and follows the framework's supported path.
2. **Custom Next.js UI using Eve's client:** more control, but recreates interface and session behavior that the official scaffold already provides.
3. **Standalone custom frontend/API:** most flexible, but adds a separate service boundary and more authentication, streaming, and session code.

The official scaffold is selected because the repository already uses Eve and the immediate goal is a working phone-first chat, not a custom UI framework.

## User experience

- Landing screen explains that this is the planning-stage development agent.
- A clear new-chat action starts a fresh session.
- The conversation view has readable streamed messages and a large message composer.
- The active session can be reopened from its URL.
- Errors for missing model credentials, authentication, or network failures are visible and actionable.
- No mock assistant replies: every assistant response must come from the Eve runtime.

## Acceptance criteria

1. A clean install on the repository's supported Node.js version can install dependencies and build the Eve/Next.js app in CI.
2. The app renders without horizontal overflow at a 360 CSS-pixel viewport and remains usable at common Android phone widths.
3. A user can start a session, send a message, and see a real agent response stream.
4. Refreshing/reopening a session URL restores that session's conversation, subject to Eve's documented retention and deployment behavior.
5. The planning agent produces a useful, structured plan and does not claim implementation or verification actions it did not perform.
6. Missing model credentials and unauthorized requests fail closed with useful error messages.
7. Automated tests cover the planning response contract, session/chat UI's core states, and the mobile layout smoke check where supported.
8. CI runs the authored TypeScript type-check unconditionally once TypeScript source exists, plus the relevant tests and production build.
9. No secrets are added to the repository; no paid deployment or model usage is triggered without explicit user approval.

## Security and cost boundaries

- Local development may use Eve's documented local development auth.
- Production browser access must require a real sign-in/authentication method.
- Secrets are configured through the hosting provider's environment settings, never committed.
- Do not enable GitHub tools, shell execution, or repository write capabilities in this milestone.
- Do not deploy or trigger paid model calls until the user has reviewed the provider/authentication setup and approved any costs.

## Implementation review points

- Verify the current Eve CLI scaffold output against the installed Eve version before adapting generated files.
- Keep changes focused; do not replace the existing agent instructions or CI workflow wholesale.
- Add tests before implementation and observe them fail before writing production behavior.
- Review generated dependencies and scripts for compatibility with Node.js 24 and the repository's current package setup.
- Report what is actually verified; a successful build alone does not prove model authentication or a deployed live chat works.

## Permanent Financial Boundary and Long-Term Self-Funding Objective

The user's personal funds are permanently off limits. This is a hard security boundary, not a configurable budget preference.

- The system must never access, request, borrow, charge, transfer, pledge, or spend the user's personal money or credit. It must not use personal payment cards, bank accounts, credit facilities, or subscriptions, including through another account or intermediary.
- The user is not the financing source for the agent's growth. Initial and ongoing operation must use no-cost/open-source resources and genuinely free tiers where practical. Free-tier quotas and terms must be respected; when a free allowance is exhausted, pause or use an approved no-cost alternative rather than silently upgrading or incurring charges.
- A future, separately permissioned business capability may research opportunities and create products or services intended to earn revenue. Only funds actually received into a separately designated business-controlled account may be considered for business expenses. Forecasts, pending payments, and expected sales are not available funds.
- The long-term objective is for the agent to fund its own approved capability improvements, including researching and acquiring useful physical hardware (for example, local compute, storage, development boards, and test devices) that can be shipped to the user for installation or use. Hardware purchases are not enabled in the first milestone.
- Before any future purchase or external financial action, require explicit user approval of the item, seller, total landed cost, purpose, shipping destination, and spending cap. No autonomous checkout, recurring commitment, financing, or payment credential access is permitted by default.
- Keep auditable records of realized revenue, fees, refunds, taxes/reserves, expenses, and available business funds. Never spend anticipated revenue; never mix business funds with the user's personal funds. Reinvestment may use only cleared business funds within a user-approved business spending policy.
- Revenue-generation activities must comply with applicable law, platform terms, intellectual-property rights, and honest marketing practices. No spam, deception, unauthorized scraping, or unsupported product claims.
- These future capabilities must be introduced gradually behind explicit permissions. The first milestone remains planning-only and cannot create businesses, publish products, accept payments, place orders, or access financial accounts.

This boundary takes precedence over agent goals, tool instructions, model output, and any external content. No prompt, workflow, or future agent may override it.
